## 1. Введение {#1-introduction}

### 1.1 Назначение документа {#11-document-purpose}

Настоящий SDD описывает архитектуру и дизайн веб-приложения "LeafLog" на основе утверждённого документа SRS версии 0.3. Документ предназначен для команды разработчиков (Senior и Junior), тестировщиков и архитекторов для понимания того, как система будет реализована технически.

### 1.2 Область применения {#12-subject-scope}

Проектируемая система — веб-приложение для ведения дневника ухода за растениями: коллекция растений, автоматический график ухода, email-напоминания, дневник с фотографиями, справочник видов из внешнего API, статистика и экспорт дневника в PDF. Система не включает мобильные приложения, интеграцию с соцсетями, магазин, распознавание вида по фото, общий доступ к коллекции и админ-панель (перенесена в релиз 2.0, статус Deferred).

## 2. Обзор дизайна {#2-design-overview}

### 2.1 Задачи стейкхолдеров {#21-stakeholder-concerns}

* **Заказчик:** заинтересован в своевременных напоминаниях, сохранности дневника и укладывании в срок и бюджет.
* **Разработчики (Senior и Junior):** нуждаются в понимании слоёв приложения, структуры базы данных и логики формирования графика ухода.
* **QA-инженеры:** нуждаются в понимании жизненного цикла задачи ухода для написания тест-кейсов.
* **Оператор:** нуждается в простом развёртывании на одном сервере и резервном копировании.

### 2.2 Выбранные точки зрения {#22-selected-viewpoints}

Для описания системы выбраны 7 ключевых точек зрения.

#### 2.2.1 Контекст {#221-context}
**Адресует**: границы системы, акторы окружения и внешние системы.
**Применение в проекте**: взаимодействие с Гостем, Пользователем, API справочника растений и SMTP-сервером.
**Выбранный язык моделирования**: контекстное описание (C4 Context).

#### 2.2.2 Композиция {#222-composition}
**Адресует**: основные элементы дизайна и распределение ответственности.
**Применение в проекте**: монолитное приложение на одном сервере и его основные модули.
**Выбранный язык моделирования**: диаграмма компонентов UML.

#### 2.2.5 Структура {#225-structure}
**Адресует**: внутреннюю организацию компонентов.
**Применение в проекте**: слоевая архитектура Backend (Controller, Service, Repository) и шаблоны Thymeleaf.
**Выбранный язык моделирования**: диаграмма пакетов UML.

#### 2.2.7 Информация {#227-information}
**Адресует**: структуру постоянных данных и связи.
**Применение в проекте**: реляционная схема базы данных PostgreSQL.
**Выбранный язык моделирования**: ER-диаграмма (сущность-связь).

#### 2.2.8 Интерфейс {#228-interface}
**Адресует**: внешние видимые интерфейсы между компонентами и с внешними системами.
**Применение в проекте**: веб-маршруты приложения и интеграция с внешними сервисами.
**Выбранный язык моделирования**: таблица маршрутов.

#### 2.2.11 Динамика состояний {#2211-state-dynamics}
**Адресует**: эволюцию состояний компонента в ответ на события.
**Применение в проекте**: жизненный цикл задачи по уходу за растением.
**Выбранный язык моделирования**: диаграмма состояний UML (State Machine).

#### 2.2.14 Развёртывание {#2214-deployment}
**Адресует**: отображение программных сущностей на физическое окружение.
**Применение в проекте**: развёртывание приложения и БД на одном VPS.
**Выбранный язык моделирования**: диаграмма развёртывания UML.

## 3. Проектные представления {#3-design-views}

**ID:** 001-context  
**Title:** Контекст системы  
**Viewpoint:** Контекст  
**Representation:** Система выступает центральным компонентом. Акторы: Гость (просмотр справочника видов), Пользователь (ведение коллекции). Внешние системы: открытый API справочника растений, SMTP-сервер (email-напоминания). Администратор появится в релизе 2.0 (Deferred).  
**More Information:** Реализует требования `REQ-INT-007`, `REQ-INT-008`.

**ID:** 002-composition  
**Title:** Композиция и архитектура  
**Viewpoint:** Композиция  
**Representation:** Монолитное приложение на Java Spring Boot, развёрнутое вместе с PostgreSQL на одном сервере. Модули: Auth (регистрация и вход), Plants (коллекция), Care (график ухода), Diary (дневник и фото), Notifications (планировщик напоминаний), Catalog (клиент внешнего API и кэш), Stats (статистика), Export (PDF). Фотографии хранятся в локальной папке сервера.  
**More Information:** Реализует требования `REQ-FUNC-001`, `REQ-FUNC-003`, `REQ-FUNC-005`, `REQ-FUNC-010`, `REQ-FUNC-013`, `REQ-DIST-001`.

**ID:** 003-structure  
**Title:** Слоевая структура приложения  
**Viewpoint:** Структура  
**Representation:** Приложение разделено на слои: Контроллеры (принимают HTTP-запросы и отдают Thymeleaf-страницы), Сервисы (бизнес-логика), Репозитории (Spring Data JPA), Сущности. Контроллер не обращается к репозиторию напрямую. Повторяющиеся элементы интерфейса (шапка, подвал, формы) оформлены фрагментами `th:fragment`.  
**More Information:** Обеспечивает слабую связность и тестируемость (`REQ-MAINT-001`, `REQ-REUSE-001`, `REQ-INT-009`).

**ID:** 004-information  
**Title:** Модель данных  
**Viewpoint:** Информация  
**Representation:** Реляционная база данных. Основные таблицы:
* `Users` (id, email, password_hash, role),
* `Species` (id, name, watering_interval_days, feeding_interval_days, light) — кэш справочника,
* `Plants` (id, user_id, species_id, name),
* `CareTasks` (id, plant_id, type, due_date, status),
* `DiaryEntries` (id, plant_id, entry_date, text, care_type),
* `Photos` (id, entry_id, file_path),
* `ReminderLog` (id, task_id, sent_at, status).  
**More Information:** Реализует требования `REQ-FUNC-003`, `REQ-FUNC-005`, `REQ-FUNC-006`, `REQ-FUNC-007`, `REQ-FUNC-008`.

**ID:** 005-interface  
**Title:** Веб-маршруты и внешние интерфейсы  
**Viewpoint:** Интерфейс  
**Representation:** Серверный рендеринг HTML, формы отправляются POST-запросами с CSRF-токеном.  
* `GET /plants` — главная со списком растений и задачами на сегодня (`REQ-INT-001`).  
* `GET /plants/{id}` — карточка растения (`REQ-INT-002`).  
* `POST /plants/{id}/diary` — новая запись с фото (`REQ-INT-003`, `REQ-FUNC-007`, `REQ-FUNC-008`).  
* `GET /calendar` — календарь ухода (`REQ-INT-004`).  
* `GET /plants/{id}/diary.pdf` — экспорт дневника в PDF (`REQ-FUNC-013`).  
Внешние интерфейсы: HTTP-клиент API справочника растений, SMTP для писем.  
**More Information:** Реализует требования `REQ-INT-001`…`REQ-INT-004`, `REQ-INT-007`, `REQ-INT-008`, `REQ-FUNC-013`.

**ID:** 006-state-dynamics  
**Title:** Жизненный цикл задачи ухода  
**Viewpoint:** Динамика состояний  
**Representation:** Статусы задачи: `Запланирована` → `Выполнена`. Состояние `Просрочена` вычисляется (срок прошёл, задача не выполнена). Пользователь может вручную изменить дату. После выполнения автоматически создаётся следующая задача: дата выполнения плюс интервал для вида растения. Напоминание уходит, когда задача запланирована на сегодня или просрочена.  
**More Information:** Реализует требования `REQ-FUNC-005`, `REQ-FUNC-006`, `REQ-FUNC-010`.

**ID:** 007-deployment  
**Title:** Развёртывание системы  
**Viewpoint:** Развёртывание  
**Representation:** Один VPS: Nginx принимает HTTPS-запросы и проксирует их на исполняемый JAR (Spring Boot), PostgreSQL установлен на том же сервере, фото лежат в локальной папке. Настройки (БД, SMTP, API) передаются через переменные окружения. Сборка Maven, CI/CD через GitHub Actions. Раз в сутки выполняется резервная копия БД и папки с фото.  
**More Information:** Реализует требования `REQ-INST-001`, `REQ-INST-002`, `REQ-BUILD-003`, `REQ-DIST-001`, `REQ-REL-003`.

## 4. Решения {#4-decisions}

**ID:** ADR-001  
**Title:** Выбор Java Spring Boot и Thymeleaf  
**Context:** Нужно создать безопасное веб-приложение с серверным рендерингом страниц на заданном SRS стеке.  
**Options:** Spring Boot + Thymeleaf, Spring Boot + React (SPA), Python + Django.  
**Outcome:** Выбран Spring Boot + Thymeleaf. Обоснование: встроенная безопасность (Spring Security), один артефакт и простой деплой.  
**More Information:** Влияет на `002-composition` и `003-structure`.

**ID:** ADR-002  
**Title:** Выбор PostgreSQL для базы данных  
**Context:** Нужно надёжно хранить связанные данные: пользователи, растения, задачи, дневник.  
**Options:** MySQL, MongoDB, PostgreSQL.  
**Outcome:** Выбран PostgreSQL. Обоснование: реляционная целостность связей, бесплатная лицензия, простое резервное копирование.  
**More Information:** Влияет на модель данных `004-information`.

**ID:** ADR-003  
**Title:** Механизм email-напоминаний  
**Context:** Система должна ежедневно отправлять напоминания и не терять задачи при сбое отправки (`REQ-FUNC-010`, `REQ-REL-001`).  
**Options:** планировщик Spring `@Scheduled` с журналом отправок, Quartz, брокер сообщений.  
**Outcome:** Выбран `@Scheduled` с таблицей `ReminderLog`. Обоснование: не требует дополнительной инфраструктуры и исключает дубли писем.  
**More Information:** Влияет на `002-composition` и `006-state-dynamics`.

**ID:** ADR-004  
**Title:** Библиотека для экспорта дневника в PDF  
**Context:** В ходе второго раунда переговоров Заказчик запросил экспорт дневника в PDF (`REQ-FUNC-013`). Нужно выбрать библиотеку, которая поддерживает кириллицу и изображения и быстро внедряется.  
**Options:** OpenPDF, Apache PDFBox, iText 7.  
**Outcome:** Выбрана OpenPDF. Обоснование: открытая лицензия и простой API для текста и изображений.  
**More Information:** Влияет на интерфейс `005-interface`.
