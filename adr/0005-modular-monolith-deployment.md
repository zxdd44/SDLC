# Модульный монолит и развёртывание единым JAR за Nginx

## Контекст и постановка задачи
Нужно зафиксировать, из каких модулей состоит LeafLog, как они взаимодействуют и как размещаются на сервере. Требования: один сервер (`REQ-DIST-001`), исполняемый fat-jar (`REQ-BUILD-002`), хостинг до 20 USD в месяц (`REQ-COST-001`), конфигурация через переменные окружения (`REQ-INST-002`).

## Драйверы решения
* Простое развёртывание на одном VPS.
* Слабая связность модулей и тестируемость (`REQ-MAINT-001`).
* Ограниченный бюджет и срок MVP.

## Рассмотренные варианты
* Модульный монолит: модули с интерфейсами в одном fat-jar
* Микросервисы
* Монолит без выделенных интерфейсов модулей

## Итог решения
Выбран вариант **«Модульный монолит»**: модули взаимодействуют через интерфейсы, приложение собирается в один `leaflog.jar` и запускается в JVM за Nginx.

### Последствия
* **Хорошо**, потому что один артефакт, одна БД и простое резервное копирование.
* **Плохо**, потому что нет независимого масштабирования модулей.

### Подтверждение
Проверка сборки Maven (один исполняемый JAR) и ревью зависимостей между модулями.

## Плюсы и минусы вариантов

### Модульный монолит
* Хорошо, потому что простое развёртывание при чётких границах модулей.
* Плохо, потому что границы нужно контролировать дисциплиной.

### Микросервисы
* Хорошо, потому что независимое масштабирование.
* Плохо, потому что избыточно для MVP, дороже хостинг и сопровождение.

### Монолит без интерфейсов
* Хорошо, потому что быстрее начать.
* Плохо, потому что высокая связность и сложное тестирование.

## Дополнительная информация
* Связанные требования SRS: `REQ-DIST-001`, `REQ-BUILD-002`, `REQ-INST-002`, `REQ-MAINT-001`.
* Связанные элементы SDD: `002-composition`, `007-deployment`.
* **Диаграмма компонентов (`uml/component.png`).**
  * **Подсистема** `«subsystem» LeafLog` содержит компоненты Web, Auth, Plants, Care, Diary, Catalog, Stats, Export, Notifications и Persistence.
  * **Предоставляемый интерфейс** («леденец») показывает, что компонент даёт: `IAuth`, `ICareService`, `IStats`, `ICatalog`, `IPdfExport`, `IPlantService`, `IDiaryService`.
  * **Требуемый интерфейс** («гнездо») показывает, что компонент использует: `Web` требует интерфейсы сервисов, а все модули данных требуют `IRepository`, который предоставляет `Persistence (Spring Data JPA)`.
  * **Сборочный коннектор** (шарик в гнезде) соединяет требуемый интерфейс одного компонента с предоставляемым интерфейсом другого.
  * **Зависимость** (пунктирная стрелка): `Export` зависит от `IDiaryService` и `IPlantService`.
  * **Порты** (маленькие квадраты на границе) и **делегирующие коннекторы** выводят внутренние интерфейсы наружу: `Web UI (HTTPS)`, `Species Data (HTTPS, REST)`, `Send Mail (SMTP)`, `SQL (JDBC)`. Внешние системы показаны как `«subsystem»`.
* **Диаграмма развёртывания (`uml/deployment.png`).**
  * **Узел** `«device» VPS Server (Linux)` содержит среды выполнения `«executionEnvironment»`: Nginx, JVM (Java 21), PostgreSQL.
  * **Артефакт** `«artifact» leaflog.jar` содержит вложенные папки `BOOT-INF/lib` (библиотеки `leaflog-*.jar`, `openpdf.jar`) и `BOOT-INF/classes` (`application.yml`, шрифт).
  * **Манифестация** `«manifest»` (пунктирная стрелка) показывает, какой компонент реализует артефакт: `leaflog-plants.jar` → `Plants`, `leaflog-diary.jar` → `Diary`, `leaflog-export.jar` → `Export`.
  * **Каналы связи** подписаны протоколами: `HTTP (localhost:8080)` между Nginx и JVM, `JDBC (TCP 5432)` до PostgreSQL, `Local FS` до папки `/var/leaflog/photos`.
  * **Соответствие моделей.** Интерфейсы компонентов соответствуют классам: `IPlantService` ↔ `PlantService`, `IPdfExport` ↔ `PdfGenerator`, `IRepository` ↔ репозиториям Spring Data JPA.
