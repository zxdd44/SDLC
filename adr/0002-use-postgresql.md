# Выбор PostgreSQL в качестве основной СУБД

## Контекст и постановка задачи
Приложению нужно хранить связанные данные: пользователей, растения, задачи ухода, записи дневника и ссылки на фото. Потеря или рассогласование данных дневника недопустимы.

## Драйверы решения
* Целостность связей между сущностями (растение → задачи → записи).
* Бесплатная лицензия (`REQ-COST-001`).
* Простое резервное копирование (`REQ-REL-003`).

## Рассмотренные варианты
* MySQL
* MongoDB (NoSQL)
* PostgreSQL

## Итог решения
Выбран вариант **«PostgreSQL»**, так как он обеспечивает строгую целостность данных и бесплатен.

### Последствия
* **Хорошо**, потому что транзакции и внешние ключи не дают потерять связанные данные.
* **Плохо**, потому что требует базовых навыков администрирования и настройки резервного копирования.

### Подтверждение
Проверка через анализ схемы базы данных (ER-диаграмма) и тест восстановления из резервной копии.

## Плюсы и минусы вариантов

### MySQL
* Хорошо, потому что проще в настройке.
* Плохо, потому что уступает PostgreSQL в продвинутых возможностях.

### MongoDB
* Хорошо, потому что гибкая схема.
* Плохо, потому что данные проекта явно реляционные, и целостность связей пришлось бы обеспечивать кодом.

### PostgreSQL
* Хорошо, потому что надёжная реляционная СУБД с открытым кодом.
* Плохо, потому что требует администрирования.

## Дополнительная информация
* Связанные требования SRS: `REQ-REL-003`, `REQ-COST-001`.
* Связанные элементы SDD: `004-information`.
